# Trinkies cosmetics integration

Trinkies is Aerix Launcher's client-side cosmetics bridge. Gradle is configured to build the Fabric JAR from `:aerix_client_mod`, include it in the Android APK as `components/aerix_client/aerix_client_mod.jar`, and package the generated item source under `assets/trinkies/`. The launcher is configured to package the same source directory as `trinkies/` assets. Both paths are built and checked in CI: the debug workflow compiles the APK with the JAR embedded and verifies the JAR's packaged catalog, so a missing or mislabeled asset fails the build instead of quietly failing in game.

## Install scope and file safety

- Existing Fabric-family and Aerix Client instances are checked locally when Home opens; a supported instance is checked again before launch. Vanilla, Forge, and NeoForge are not modified and Fabric is not silently installed for them.
- The managed artifact path is `<instance>/mods/trinkies-aerix.jar`. `<instance>/mods/trinkies-aerix.manifest.json` records schema, mod ID, version, artifact name, and SHA-256 for the exact managed JAR.
- An existing JAR is only updated when the manifest proves it is the prior managed byte sequence. A duplicate `trinkies` mod ID, legacy `aerix-client-animator.jar`, malformed manifest, or unowned target is left untouched and reported. The installer does not delete legacy JARs and does not fall back to overwriting a target after an atomic rename failure.
- The sidecar is an ownership/hash record, not a malware scan. Review unexpected mod conflicts manually. Turning Trinkies off is launcher-wide (the Wardrobe's `TRINKIES COSMETICS` line): it serves the account skin unbaked, leaves the cape to the launcher's own designs, and writes an emptied loadout so a running client unequips rather than keeping its last wardrobe. The next line, `COSMETICS ON IN <INSTANCE>`, narrows the same decision to the instance the launcher would start next - see below. Version-matched JAR selection remains unfinished.

## Per-instance cosmetics opt-out

- The state is a marker file, `<instance>/trinkies/disabled`, not a new `Instance` field. `instances.json` is read and written by several code paths, and a Gson boolean absent from an old file silently defaults - for an "enabled" flag that means every existing instance loses its cosmetics the moment it is upgraded. A marker has no schema to age: it travels with the folder through any copy or backup, and it sits beside the `equipped.json` it is the counterpart of. Cosmetics are on unless the file exists.
- Flipping it re-syncs that instance immediately: the cape frames are rewritten without the wardrobe patch, and the loadout is written emptied, so a game already running follows on its next poll instead of waiting for the next launch. `TrinkiesLoadout.writeForInstance` consults the marker itself rather than trusting its caller, which is why a global re-push, a pre-launch repair, and a toggle can never disagree.
- It declines *cosmetics*, not the mod: the Trinkies JAR stays installed and the launcher's own animated cape stays served, because neither is what the switch is about. `config/aerix_cape_frames/meta.properties` records `trinkiesBack=none` for an opted-out instance so the mod's bake cross-check reads the player's choice as agreement, not as a mismatch.
- The launcher's Wardrobe preview keeps showing the outfit while an instance is opted out. That is deliberate: the preview belongs to the account and the wardrobe, and only what the skin server hands to a running game is per-instance.

## Current source-tree behavior

- The launcher preview uses the account's local/cached/service skin where available, supports classic/slim model selection, existing cape paths, and a 2D fallback when WebGL is unavailable.
- Existing account skins, saved skin presets, 15 original animated cape designs, imported capes, and the shared catalog are retained. All 300 catalog items are selectable, one per wardrobe slot (`hat`, `suit`, `back`, `pet`, `emote`, `aura`). Equipping bakes each item's `garment.png` patch over the account skin in UV space before that skin is served to the game, and the same ids are written atomically to `<instance game directory>/trinkies/equipped.json` before a supported instance starts. The bake needs a custom skin to paint on: on a plain account skin there is nothing to overlay. No launcher code knows what any individual item looks like - item ids, palettes and geometry live only in the catalog and its assets, and `tests/trinkies_integration_smoke.py` fails if launcher Kotlin names a catalog item. Nothing here has been visually verified in Minecraft; skin/cape visibility to other players depends on the account/skin service and server.
- `trinkies_assets/` contains 300 deterministic original assets: 50 hats, suits, back items, pets, emotes, and auras/trails each. Every item folder holds the Blockbench model and its own texture, a 192×192 `preview.png` of the mannequin actually wearing the item, and the `garment.png` bake patch (back items add a 64×32 `cape_patch.png`, laid out in the cape's own UV space, which the launcher bakes onto both the preview and the cape sheet it serves to the game). Art is authored once, in `tools/trinkies_assets/garments.py`, against the skin layout in `mc_skin_render.py`, so the patch and the card preview cannot drift apart.
- The launcher bake (`TrinkiesGarmentComposite`) is the only cosmetic *renderer* that runs today. The client mod does consume `equipped.json`: `TrinkiesLoadout` validates it against the packaged catalog (same six slots, same `^trinkies:[a-z0-9_]+$` id pattern, no unknown fields), takes the cape frame cadence from the equipped back or aura item's own `animations.json` idle clip, cross-checks that the baked frames in `config/aerix_cape_frames/meta.properties` were baked for that loadout, and writes `trinkies/applied.json` as a receipt the Wardrobe displays. The emote wheel is a real control. The Wardrobe preview panel lists eight slots under the mannequin; tapping one opens the emote list and binds a key, `UNBIND` clears it, and the binding is written to every supported instance's `trinkies/equipped.json` immediately (the mod re-reads that file on its own clock, so a rebind does not need a restart). In game the slots are the number keys and a press plays that item's own clip - `play` for the emotes the picker offers, `signature` for a pet's flourish, and a short default for anything that ships neither - as a cape flourish at that length, plus the client's arm swing where the runtime exposes one. The durations are real generated data, not constants: `play` is 2.2 s or 3.0 s depending on the item and `signature` is 2.8 s, read through `TrinkiesLoadout.playClipMillis`, which clamps to 0.25..6 s so a wild clip length cannot freeze the animator - and `applied.json` answers with how many of the eight bindings the client actually accepted, which the Wardrobe prints next to the receipt. Keys are polled through LWJGL reflectively rather than registered as a Fabric keybind, because keybind registration changed shape across the supported versions. No window handle, no LWJGL, or an empty wheel simply means a silent wheel. The runtime matrix asserts the
data path (bindings seeded, bindings accepted) but not the physical press: Fabric's client GameTest input
layer dispatches `TestInput.holdKey` straight into `KeyMapping`s, so a synthetic press never reaches the
native key state the wheel polls, and an assertion built on it would prove nothing about a real tap. There is still no pet follower, floating 3D prop, or particle trail; those remain catalog previews.

Wardrobe cloud sync is opt-in, off by default, and carries ids only. Turning it on in the Wardrobe adds
three taps - back up, restore, erase - that read and write one `wardrobe_sync` row belonging to the
signed-in Aerix account (`supabase/step4-wardrobe.sql`: self-only row-level security, a 4 KB jsonb cap,
a delete policy so the copy can be forgotten; that step has been applied to the social project and read back from
`pg_policy`, but the round trip itself has only been reviewed, not run from a device). A payload is six slot ids plus eight wheel bindings: no
skin, no cape, no texture, no preview, because the launcher rebuilds all of that from the catalog it
already ships. Restore re-validates every id against the local catalog, unequips slots the copy did not
mention, and rewrites the instance loadouts so a running client follows; an id this pack no longer
carries is skipped and reported rather than guessed at. There is no timer, no launch-time fetch and no
other-player broadcast - a wardrobe follows the Aerix account, not the Minecraft identity, and only when
the player asks. JSON Schema, texture/model/garment budget, palette, UV, animation-clip, manifest, and pack-size checks are in `tools/trinkies_assets/validate_catalog.py`.
- The full catalog passes offline structural validation, but remains marked unverified in-game. The generated contact sheets are texture/model previews, not Minecraft screenshots or art approval. Android and mod-JAR builds for this branch are green in CI, including a plain-JVM run of the loadout reader against the shipped catalog (`tests/trinkies_loadout_jvm.py`). The approved Fabric runtime matrix also runs the reader inside a real booting client: the harness writes a wardrobe, waits for `trinkies/applied.json`, and requires the client to report the hat it should wear, a cape pace stretched by the item's own animation clip, and a *refusal* when a hat id is put in the back slot. That is in-game verification of the contract, not of appearance: no screenshot or art review has happened, and nothing here draws 3D attachments.

## Visibility, sync, and privacy limits

The current Fabric mod is client-only. It includes existing local cape/texture bridges, client display overrides, the `equipped.json` reader described above, and the keybound emote wheel; it does not include the generated 3D attachments for wings/pets/auras, a pet follower, particle trails, or a synchronized multiplayer cosmetics protocol. Cosmetics reach the game today because the launcher bakes them into the served skin, not because the mod draws them. Other players are not guaranteed to see custom skins/capes, and unmodified vanilla clients/servers cannot display Trinkies-only attachments or animations.

No Trinkies cosmetic state is sent to Supabase and no cosmetics sharing opt-in/delete UI exists yet. Existing Aerix social features use Supabase separately. Offline account cosmetics remain local; no UUID sharing is added by this integration. See [`wardrobe/SPEC.md`](wardrobe/SPEC.md) before any future sync work.
